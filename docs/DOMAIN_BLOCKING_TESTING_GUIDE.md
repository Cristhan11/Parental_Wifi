## Test 1: Basic Domain Blocking (Single Domain)

**Objective:** Verify that blocking a single domain prevents access to that domain.

**Status:** ✅ Tested and Working (December 8, 2025)

**Note:** This test was successfully completed. The system correctly blocks domains via dnsmasq DNS blocking.

### Step 1: Create Blocked Website via Web Interface

1. Open your web browser and navigate to: `http://[PI_IP]/blocked-websites/create`
   - Replace `[PI_IP]` with your Pi's IP address

2. Fill in the form:
   - **Device:** Select `CP_ChildDev01` (e6:6a:8f:19:be:b1)
   - **URL/Domain:** Enter `example.com` (or any test domain like `facebook.com`)
   - **Block Type:** Select `Domain`
   - **Block Subdomains:** Leave unchecked (we'll test this in Test 2)
   - **Reason (optional):** Enter "Test blocking"

3. Click **"Block Website"** button

4. You should see a success message: "Website blocked successfully."

**What Happens Behind the Scenes:**
- `BlockedWebsiteController@store()` creates the database record
- `DomainBlockingService->blockDomainForDevice()` is called
- `block_domain.sh` script adds the domain to the config file
- `update_dnsmasq_blocklist.sh` regenerates the complete config from database (ensures consistency)
- dnsmasq is reloaded to apply changes

### Step 2: Verify Database Record

On your Pi terminal, run:

```bash
cd /var/www/parental_wifi
php artisan tinker
```

Then in tinker, run:

```php
$blocked = App\Models\BlockedWebsite::latest()->first();
```

**Expected Output:**
```

```

**Note:** The MAC address in the database may be lowercase, but the config file uses uppercase. This is normal - the scripts normalize MAC addresses to uppercase format.

Type `exit` to leave tinker.

### Step 3: Verify dnsmasq Configuration

**Important:** MAC addresses in config filenames are normalized to uppercase with colons. The database may store lowercase, but the config file uses uppercase format.

On your Pi terminal, run:

```bash
# Check if config file was created (use uppercase MAC in filename)
# Note: Use uppercase MAC address in filename: E6:6A:8F:19:BE:B1
ls -la /etc/dnsmasq.d/blocked-domains-E6:6A:8F:19:BE:B1.conf

# Alternative: List all blocked domain config files
ls -la /etc/dnsmasq.d/blocked-domains-*.conf

# View the config file content
sudo cat /etc/dnsmasq.d/blocked-domains-E6:6A:8F:19:BE:B1.conf
```

**Expected Output:**
```
# Blocked domains for device E6:6A:8F:19:BE:B1
# Generated by update_dnsmasq_blocklist.sh
# Auto-generated - do not edit manually
# Last updated: [timestamp]

address=/example.com/127.0.0.1
```

**Note:**
- The config file is generated by `update_dnsmasq_blocklist.sh` (not `block_domain.sh` directly). This ensures the config file always matches the database state. The script reads domains from the database via stdin input.
- MAC addresses are normalized to uppercase format (E6:6A:8F:19:BE:B1) in config filenames, even if stored as lowercase in the database (e6:6a:8f:19:be:b1).
- If the file doesn't exist with lowercase MAC, try uppercase or use the wildcard pattern (`blocked-domains-*.conf`) to find it.

### Step 4: Verify dnsmasq Service

On your Pi terminal, run:


**Expected:** 
- dnsmasq should be "active (running)" with no errors
- Logs should show blocked domains returning `127.0.0.1`
- Example log entries:

- The "config ... is 127.0.0.1" message indicates dnsmasq is successfully blocking the domain

**Note:** The logs show real-time blocking activity. When a device tries to access a blocked domain, you'll see queries in the logs with `config [domain] is 127.0.0.1`, confirming the blocking is working.

## Troubleshooting

### Issue: Config File Not Created After Blocking Domain

**Symptoms:** Domain blocked in database, but config file doesn't exist or is empty

**Possible Causes:**
1. `update_dnsmasq_blocklist.sh` script not receiving domains via stdin
2. Script execution failed silently
3. MAC address normalization issue

**Solution (Fixed December 8, 2025):**
- The `DomainBlockingService::updateDnsmasqBlocklist()` method now correctly passes domains to the script via stdin
- `ScriptExecutor::execute()` was updated to support stdin input using `proc_open()`
- The script expects format: `DOMAIN:BLOCK_SUBDOMAINS` (one per line)
- Example: `facebook.com:0` (blocks only facebook.com)

**Verification:**
```bash
# Check if config file exists
ls -la /etc/dnsmasq.d/blocked-domains-*.conf

# Check config file content
sudo cat /etc/dnsmasq.d/blocked-domains-E6:6A:8F:19:BE:B1.conf

# Check Laravel logs for errors
tail -n 100 storage/logs/laravel.log | grep -i "domain\|block"
```

### Issue: Domain Not Blocked

**Symptoms:** Domain still resolves to real IP, not 127.0.0.1

**Possible Causes:**
1. Device not using Pi as DNS server
2. dnsmasq not reloaded after config change
3. Config file not created correctly

**Solutions:**

1. **Verify Device DNS Settings:**
   - On device, check network settings
   - DNS server should be Pi's IP address
   - If using DHCP, Pi should be providing DNS via dnsmasq

2. **Manually Reload dnsmasq:**
   ```bash
   sudo systemctl reload dnsmasq
   # Or restart if reload doesn't work
   sudo systemctl restart dnsmasq
   ```

3. **Check Config File:**
   ```bash
   sudo cat /etc/dnsmasq.d/blocked-domains-e6:6a:8f:19:be:b1.conf
   # Verify domain is in the file
   ```

4. **Test DNS Resolution:**
   ```bash
   dig @127.0.0.1 example.com +short
   # Should return 127.0.0.1 if blocked
   ```

### Issue: dnsmasq Not Reloading

**Symptoms:** Config file updated but changes not applied

**Solution:**
```bash
# Check dnsmasq status
sudo systemctl status dnsmasq

# Reload configuration
sudo systemctl reload dnsmasq

# If reload fails, restart
sudo systemctl restart dnsmasq

# Check for errors
sudo journalctl -u dnsmasq -n 50
```

### Issue: Multiple Devices Share Same Blocklist

**Symptoms:** Blocking a domain for one device affects all devices

**Possible Causes:**
1. MAC address normalization issue
2. Config file naming issue

**Solutions:**

1. **Verify MAC Addresses:**
   ```bash
   php artisan tinker
   ```
   ```php
   App\Models\Device::select('id','name','mac_address')->get();
   # Verify MAC addresses are in correct format (XX:XX:XX:XX:XX:XX)
   ```

2. **Check Config Files:**
   ```bash
   ls -la /etc/dnsmasq.d/blocked-domains-*.conf
   # Should have separate files for each device
   ```

3. **Verify MAC Normalization:**
   - MAC addresses should be uppercase with colons
   - Example: `E6:6A:8F:19:BE:B1` (not `e6:6a:8f:19:be:b1`)

### Issue: Cached Content Still Loading After Blocking

**Symptoms:** After blocking an app (e.g., Facebook), some videos and photos still load, even though the domain is blocked

**Possible Causes:**
1. Device/app cache storing content locally
2. Browser cache storing images/videos
3. App pre-fetching content before blocking was applied

**Explanation:**
- **This is expected behavior** - DNS blocking prevents new network requests, but cannot remove content already cached on the device
- Cached content is stored locally in:
  - App cache (mobile apps)
  - Browser cache (web browsers)
  - Device storage
- DNS blocking only affects new DNS queries - it cannot delete cached files

**Solutions:**

1. **Clear App Cache (Mobile Apps):**
   - Settings > Apps > [App Name] > Storage > Clear Cache
   - Force stop the app
   - Restart the app

2. **Clear Browser Cache (Web Browsers):**
   - Settings > Privacy > Clear Browsing Data
   - Select "Cached images and files"
   - Clear cache

3. **Disconnect and Reconnect Wi-Fi:**
   - This clears DNS cache on the device
   - Forces fresh DNS queries

4. **Verify Blocking is Working:**
   ```bash
   # Check DNS resolution (should return 127.0.0.1)
   dig @127.0.0.1 facebook.com +short
   
   # Check dnsmasq logs (should show "config [domain] is 127.0.0.1")
   sudo journalctl -u dnsmasq -f | grep -i facebook
   ```

5. **Test New Content:**
   - Try accessing new content (not previously viewed)
   - Try using app functions (search, comments, new posts)
   - These should fail because they require new network requests

**Important Notes:**
- **Cached content loading is NOT a blocking failure** - it's a device-side cache limitation
- **App functionality is effectively blocked** - new API calls, content loading, and most functions will fail
- **DNS blocking works correctly** - verified by checking DNS resolution and dnsmasq logs
- **Acceptable behavior** - Some cached content may display, but the app cannot function normally

**When to Investigate:**
- If NEW content loads (not previously cached)
- If app functions work (search, comments, new posts)
- If DNS resolution returns real IPs instead of 127.0.0.1
- If dnsmasq logs show "forwarded" instead of "config ... is 127.0.0.1"
